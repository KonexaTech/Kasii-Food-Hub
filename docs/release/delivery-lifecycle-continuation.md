# Delivery lifecycle continuation (disabled)

This continuation adds merchant-triggered signed delivery intake and authorized delivery tracking to the previous private source lookup and durable callback receiver. It preserves the approved interfaces and does not enable delivery, payments or payouts. No remote schema or resource changes have been made.

Before dispatch, the existing authenticated shop-owner API verifies the actual order owner, immutable approved quote, matching persisted fee, approved shop, explicit merchant-ready state, provider proof or separately approved COD and approved dispatch time. `preparing` is refused. The current marketplace delivery workflow uses merchant-selected `out_for_delivery` as its explicit readiness signal; physical pickup is recorded only by a trusted delivery callback. Cake never dispatches solely from a customer-selected date. Existing custom cake requests are not automatically converted into ordinary delivery orders.

POST /api/owner/orders/:id/delivery sends only {version:1,source_order_id} to POST /v1/delivery/jobs, using the agreed source-specific HMAC-SHA256 canonical request. Redirects are refused and requests time out after eight seconds. Delivery independently fetches the trusted source snapshot and deduplicates by source/order. A lost response returns an error with a safe retry; successful acknowledgements pin one immutable job to the local order. Concurrent duplicate responses converge under an order-row lock. A callback arriving before the acknowledgement is pinned safely; a conflicting job is rejected. No price, commission, payment or order-completion state is inferred from any delivery event.

GET /api/orders/:id/delivery rechecks customer/owner/admin authorization and returns only delivery status, job ID, event time and a clear queued warning while searching. Existing Track controls include these fields only when dispatch is configured. The existing secondary owner page exposes the delivery request button only after an authenticated capability check. Unconfigured deployment keeps the button hidden. No driver identity, precise location, addresses or private keys are returned by tracking. First persisted intake and changed callback states atomically create existing supported `order_status` notifications for the customer and merchant. Duplicate/older events and repeated acknowledgements do not duplicate these records. These are in-app database notifications; push/WhatsApp/closed-app delivery is NOT VERIFIED. Runtime notification INSERT grants/RLS require separate staging review; denial rolls back state/receipt rather than acknowledging an undelivered record.

The Delivery continuation adds this optional directional callback field; its legacy fallback uses hmacKeyBase64 in both directions. No credentials have been transferred by this continuation.
